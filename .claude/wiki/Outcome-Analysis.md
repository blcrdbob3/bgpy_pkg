## Purpose and Scope

This page documents the outcome analysis system in BGPy, which determines the result of each simulation trial by analyzing the final routing state after BGP propagation completes. The `ASGraphAnalyzer` class and its variants examine each AS's local RIB to classify outcomes as attacker success, victim success, or disconnection. This analysis forms the foundation for all metrics and visualizations generated by the framework.

For information about how outcomes are aggregated across trials, see [Data Aggregation](/blcrdbob3/bgpy_pkg/8.2-data-aggregation). For details on how the simulation engine produces the routing state that is analyzed, see [Simulation Class and Execution Pipeline](/blcrdbob3/bgpy_pkg/4.1-simulation-class-and-execution-pipeline).

---

## Overview

After the `SimulationEngine` completes BGP announcement propagation, the `ASGraphAnalyzer` examines the final routing state to determine what happened at each AS in the network. The analyzer supports two analysis modes:

1. **Data Plane Analysis**: Recursively traces back through `next_hop_asn` fields to determine where traffic actually flows
2. **Control Plane Analysis**: Examines announcement origins to determine what each AS believes about route origins

The analyzer produces a dictionary mapping each AS to an outcome value, which is then aggregated across trials to generate metrics and graphs.

**Sources:**[bgpy/simulation_framework/as_graph_analyzers/as_graph_analyzer.py1-187](https://github.com/blcrdbob3/bgpy_pkg/blob/39199d7d/bgpy/simulation_framework/as_graph_analyzers/as_graph_analyzer.py#L1-L187)

## Data Plane Analysis

Data plane analysis determines where traffic actually flows by recursively tracing back through routing tables using the `next_hop_asn` field. This reflects real packet forwarding behavior.

**Data Plane Traceback Flowchart**: Illustrates the recursive algorithm that follows `next_hop_asn` references until reaching a base case (attacker, victim, or disconnection).

The `_get_as_outcome_data_plane` method implements a depth-first search with memoization:

1. **Check cache**: If the AS outcome is already computed, return it immediately
2. **Get announcement**: Retrieve the most specific announcement from the precomputed dictionary
3. **Determine base case**: Check if this AS is an attacker, victim, disconnected, or forms a loop
4. **Recurse if undetermined**: Follow `next_hop_asn` to the next AS and recurse
5. **Cache and return**: Store the result before returning to avoid recomputation

### Next Hop vs AS Path

Starting in BGPy v4, the traceback follows `next_hop_asn` rather than the next ASN in the `as_path`. This design choice:

- **Reflects real BGP behavior**: Routers forward based on next hop, not AS path
- **Enables origin spoofing attacks**: Attackers can forge origins while maintaining valid forwarding
- **Separates control and data planes**: AS path shows advertised path; next hop shows actual forwarding

**Sources:**[bgpy/simulation_framework/as_graph_analyzers/as_graph_analyzer.py104-109](https://github.com/blcrdbob3/bgpy_pkg/blob/39199d7d/bgpy/simulation_framework/as_graph_analyzers/as_graph_analyzer.py#L104-L109)

**Control Plane Analysis Flowchart**: Shows the simpler, non-recursive logic that examines only the announcement origin field.

The control plane analysis is straightforward:

1. **No announcement**: Return `DISCONNECTED` (AS has no route)
2. **Origin is attacker**: Return `ATTACKER_SUCCESS` (AS learned attacker's route)
3. **Origin is victim**: Return `VICTIM_SUCCESS` (AS learned legitimate route)
4. **Other origin**: Return `DISCONNECTED` (route from unexpected origin)

This analysis captures what ASes *believe* about routes based on BGP advertisements, which may differ from actual traffic flow in the data plane.

## Outcome Enumeration

The `Outcomes` enum defines all possible analysis results:

```
class Outcomes(Enum):
    ATTACKER_SUCCESS = 0   # Traffic flows to attacker
    VICTIM_SUCCESS = 1     # Traffic flows to victim
    DISCONNECTED = 2       # No route exists
    UNDETERMINED = 3       # Internal state during recursion
    DATA_PLANE_LOOP = 4    # Forwarding loop detected
```

### Outcome Semantics
OutcomeData Plane MeaningControl Plane Meaning`ATTACKER_SUCCESS`Traffic reaches attackerAS learned route from attacker origin`VICTIM_SUCCESS`Traffic reaches victimAS learned route from victim origin`DISCONNECTED`No route or forwarding dead-endNo announcement or unexpected origin`DATA_PLANE_LOOP`Circular forwarding pathN/A (not used in control plane)`UNDETERMINED`Temporary state during recursionN/A (not used in control plane)
The `UNDETERMINED` outcome should never appear in final results - it indicates an internal error if it does.

## InterceptionASGraphAnalyzer

The `InterceptionASGraphAnalyzer` extends `ASGraphAnalyzer` to implement stricter success criteria for interception attacks (e.g., subprefix hijacks that should maintain connectivity to the victim).

```

Attacker at AS → Continue traceback

Next hop outcome?

VICTIM_SUCCESS

ATTACKER_SUCCESS

DISCONNECTED
```

**Interception Analysis Diagram**: Shows how `InterceptionASGraphAnalyzer` modifies the standard logic to require that traffic eventually reaches the victim for attacker success.

### Modified Behavior

When the standard analyzer encounters an attacker AS, it immediately returns `ATTACKER_SUCCESS`. The interception analyzer instead:

1. **Continues traceback**: Follows the attacker's `next_hop_asn` to see where traffic ultimately goes
2. **Requires victim reachability**: Only returns `ATTACKER_SUCCESS` if the path eventually reaches the victim
3. **Detects incomplete interception**: Returns `DISCONNECTED` if the attacker's route doesn't connect to the victim

This models scenarios where the attacker must maintain a working path to the victim (e.g., to exfiltrate data after inspection) rather than simply blackholing traffic.

**Sources:**[bgpy/simulation_framework/as_graph_analyzers/interception_as_graph_analyzer.py1-123](https://github.com/blcrdbob3/bgpy_pkg/blob/39199d7d/bgpy/simulation_framework/as_graph_analyzers/interception_as_graph_analyzer.py#L1-L123)

### Implementation Details

The `InterceptionASGraphAnalyzer` overrides two methods:
MethodPurpose`_get_as_outcome_data_plane`Adds logic to continue traceback after hitting attacker AS`_determine_as_outcome_data_plane`Maintains base case checking for attacker, victim, and disconnection
The key modification is in `_get_as_outcome_data_plane` at lines 36-71, which adds a conditional branch when `outcome_int == Outcomes.ATTACKER_SUCCESS.value` to trace through the attacker's next hop.

**Simulation Integration Sequence**: Shows when and how the analyzer fits into the broader simulation pipeline.

### Analysis Invocation

The analysis is triggered in the simulation's main trial loop:

1. **Post-propagation**: Analysis runs after all BGP rounds complete
2. **Per-trial**: Each trial gets a fresh analyzer instance
3. **Tracking flags**: `data_plane_tracking` and `control_plane_tracking` control which analyses run
4. **Outcome storage**: Results are passed to `GraphDataAggregator` for statistical aggregation
